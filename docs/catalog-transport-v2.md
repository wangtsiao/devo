# Optional catalog transport preference

Discovery fetches the existing default `https://models.dev/api.json` first. Only after successful v1 conversion, it may enrich existing exact provider/model pairs from `https://models.dev/experimental/v2.0/api.json`. Explicit custom sources and local fixtures make no additional network request. Optional v2 HTTP/JSON/projection failure retains v1; failure of the primary source retains the last successful process-local catalog as before. The optional fetch is wrapped in a separate 3-second total async budget (including body download), with the existing 32 MiB limit; the primary v1 fetch retains its 15-second budget. A slow v2 adds at most that async wait budget before v1 installation; synchronous parsing/projection time is not covered. Refresh still holds the existing global refresh gate and is not backgrounded.

The upstream published provider map is distinct from authored TOML. References: anomalyco/models.dev `packages/core/src/schema-v2.ts` (ProviderV2, ModelV2, ApiEntryV2), `generate-v2.ts` (toModelV2, resolveAuthoredApis), and README experimental API. Exported API entries are catalog assertions, including generator defaults, not probed evidence. No key is sent to models.dev and no authenticated endpoint probing or runtime retry-based protocol switching is introduced.

Preference is Messages, Responses, then Chat Completions, only among declared representable routes for chat models supporting tools. Each replacement installs endpoint, protocol and request model together. Messages bases must end in `/v1`; exactly this suffix is removed because Devo appends `/v1/messages`. Responses and Chat retain explicit non-root paths and use their existing suffixes. Host-only/root bases are skipped because the server normalizer would inject `/v1` and silently change the catalog-declared target. A lower-priority representable declared route can still be selected; otherwise the original v1 tuple remains. URL templates, userinfo, query/fragment, unsupported custom paths, nonempty protocol compatibility requirements and explicit no-tools routes are skipped. Missing or unrepresentable metadata retains the v1 route. This does not import v2 per-API capabilities, pricing or compatibility: existing v1 model metadata remains authoritative. Compatibility-sensitive adapters still require separate review/testing.

Google transport is untouched. `openai-codex` is excluded and is not requested via the API's opt-in parameter. Messages does not imply Anthropic OAuth. Existing differing request aliases retain their full v1 route rather than guessing v2 alias semantics.

## Pinning boundary and separate dependency

This patch is catalog-only, not the unmerged #405 explicit API-key login fix. It never changes stored credentials or routes. Existing effective catalog projection strips all remote route fields for configured user connections, including incomplete ones; partial custom connections require explicit repair. Startup/refresh cannot redirect their credentials.

#405 is left untouched. Its current provider-level login pinning cannot automatically pin different preferred model-level tuples from this enrichment. Before claiming explicit-connect coverage, integrate a separately reviewed selected-model pinning contract that copies the coherent tuple during an explicit connection action, retaining custom routes and credential ownership fences. Do not blindly elevate one model's route to the whole provider.

Frozen Rust tests cover preference, DeepSeek Messages path, declared fallback, absent/malformed metadata, alias/Google/OAuth exclusions, and effective user-connection stripping. They are source tests, not live provider certification. Full Rust execution and real user-authorized integration remain required before shipping.
